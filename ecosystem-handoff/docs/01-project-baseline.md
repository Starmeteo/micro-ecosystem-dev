# 项目基线与决策记录

版本：0.1-review1。依据：本次项目讨论及用户对 v0.1 生态模型、系统架构和开发准备方案的认可。本文记录产品意图，不伪装成完整逐字聊天导出。

## 1. 产品意图

用户希望在 Windows 上拥有一个可以自己布置、可以长时间欣赏、会由生态关系驱动变化的微缩世界。世界可作为较大的观赏窗口，也可成为日常桌面组件。创建不同主题的世界，各自保存历史、环境和生物。

用户对“完全模拟真实世界”的解释重点是三类关系：生物影响生物、生物影响环境、环境影响生物。画面采用用户上传的精细像素风参考；视觉写实度与科学模型精度分开讨论。

项目优先体现自主生活、可观察的生态反馈、可编辑的自然构图和可组合的桌面体验。具体规则采用有来源且可验证的简化模型，科学参数通过后续研究与校准逐步完善。

## 2. 状态与变更规则

| 标记 | 含义 | 后续怎样处理 |
| --- | --- | --- |
| D | 用户明确表达或明确选择的方向 | 保留；若发现不可行或与其他 D 冲突，展示证据和影响后请用户取舍 |
| B | 经用户认可的规划工作基线，具体细节仍可审查 | 先按此评估；调整须记录原因和影响，重大体验变化需要用户选择 |
| O | 尚未确定、等待资料或等待校准 | 给研究或实验计划；只把需要产品取舍的事项交给用户 |

本次最后指令新增 D-015：交给 Codex 后先审查，找缺漏和不明确之处，没问题后再开始开发。为让用户能阅读审查结论，本包把首轮设为仅审查，开工以用户在后续会话中明确授权为准。

## 3. 明确决定 D

| ID | 决定 | 对开发的约束 |
| --- | --- | --- |
| D-001 | Windows | 首版平台按 Windows 验证；具体支持版本另行查证 |
| D-002 | 自主生态反馈 | 每个主要行为和环境变化应能关联到模型状态或外部输入 |
| D-003 | 像素自然插画风 | 使用 references 中的 9 图作为视觉证据，不以“像素滤镜”代替素材设计 |
| D-004 | 精心布置的主视角 | 首版以固定主构图为主，允许局部观察；不要求自由三维相机 |
| D-005 | 偏自然环境切片，兼顾容器方向 | 林下、浅水池塘优先；封闭容器边界作为后续扩展 |
| D-006 | 先按林下与浅水池塘两种场景推进 | 两主题属于首版目标，允许分阶段实现 |
| D-007 | 按生态主题组织创作入口 | 每主题有典型预设，预设同时可作为开发测试样例 |
| D-008 | 修改预设另存与自由搭建均支持 | 官方预设与用户世界隔离；提供从空白开始的路径 |
| D-009 | 多个生态世界相互独立 | 不共享动态资源、随机进度、气候或生物实例 |
| D-010 | 每世界保留气候，只同步部分现实 | 现实作为边界目标；切换世界不继承另一世界参数 |
| D-011 | 隔几天打开，从上次状态继续 | 停止运行、睡眠、关机间隔不做生态补算 |
| D-012 | 恢复后昼夜逐渐对齐现实 | 先恢复生物和资源，再通过过渡更新光照节律；现实钟立即正确 |
| D-013 | 大窗口与常态小组件 | 常态仍可欣赏生态；离开一段时间出现模糊覆盖及时间等内容 |
| D-014 | 可独立创建与组合组件 | 时钟可叠在生态视图上，多个组件也可在面板中自由摆放 |
| D-015 | Codex 首轮审查，之后才开发 | 文档、原图、原型均应被检查；不能读完就直接初始化工程 |
| D-016 | 技术栈暂定 Tauri 2 + React 19 + TypeScript + PixiJS 8 + Rust | 保留大方向；具体依赖版本与兼容性由官方文档核查 |

## 4. 工作基线 B

| ID | 工作默认 | 需要审查的重点 |
| --- | --- | --- |
| B-001 | Rust 维护权威世界状态，UI 与渲染读取状态 | 内核独立于 Tauri、窗口、数据库和 OS 时钟 |
| B-002 | 应用运行时所有未暂停世界继续 | 多世界资源预算、显式暂停和关闭窗口语义 |
| B-003 | 生态编辑时暂停对应世界 | 编辑完成如何提交、保存和恢复；保留个体身份与资源后果 |
| B-004 | 试运行在完整副本上进行 | RNG、资源、时间全部复制；采用结果为明确操作 |
| B-005 | 日常先按 1:1 时间推进；调试/试运行可整体加速 | 长期成长和季节变化的可感知性，不允许只加速动物 |
| B-006 | 允许死亡和局部种群消失 | 用检查点或明确干预恢复，不偷偷补充资源或生物 |
| B-007 | 自然切片具有显式外界交换 | 输入来源、耗尽条件和气候过程可以解释和记录 |
| B-008 | 主要动物按个体，植物/微生物按斑块或种群 | 计算粒度要与画面统计和行为能力一致 |
| B-009 | 连通浅塘先用充分混合水体 | 局部氧梯度、分层和复杂水动力暂不表现为已模拟 |
| B-010 | 首版化学采用有机物、简化可利用 N/P 与氧收支 | 没有精确 NH3、pH 或硝化预测；说明氧模型适用范围 |
| B-011 | 季节先按世界自己的日历推进 | 与真实昼夜同步的组合规则，跨年及恢复行为 |
| B-012 | WebGL 作为初始渲染基线，WebGPU 后续评估 | 当前版本兼容性和真实 Windows 设备表现 |
| B-013 | 生态编辑与组件布局编辑分开 | 拖组件不改变地形；缩放视图不改变模拟面积或水量 |
| B-014 | 先做林下最小闭环，再扩展池塘和完整组件系统 | 不把首个闭环的范围误写为完整首版范围 |

| O-003 | 昼夜目标采用固定当地作息、配置地点的太阳时，或其他映射 | Codex 提本地优先方案，用户确认体验差异 | 昼夜同步实现前 |

| O-006 | 正式素材的制作方法、来源记录和动画工作量 | Codex 先评估当前工具能力并提交资源计划 | 正式美术生产前 |
| O-007 | 1:1 运行与成长/季节可感知性是否匹配 | 原型验证，用户体验评审 | 日常使用体验冻结前 |
| O-008 | 存档编码、版本迁移策略、具体随机算法和通信结构 | Codex 工程选择，记录依据 | 内核持久化合同冻结前 |

O 项不等于现在必须问用户九个问题。先调查能调查的内容，给出建议，把阻塞当前里程碑且影响产品意图的选择集中提出。

## 6. 范围边界

当前未要求账户系统、云同步、联网社交、市场交易、多人共同编辑、移动端、LLM 驱动生物、联网天气 API、自动启动或自动更新。后续若加入，应独立说明价值、依赖和成本。现阶段“组件”是产品组合能力，不自动等同于操作系统级插件协议或任意第三方代码执行。

没有确认 Windows 桌面壁纸层嵌入、全局鼠标穿透、每个组件一个原生窗口或系统级 Acrylic 模糊。先实现生态画面内部模糊与明确的窗口交互；原生桌面整合能力需按用户意图和实机验证选择。

## 7. 第一个可验收闭环

从林下预设建立世界，移动一块石头，检查原位置与新位置的遮阴/遮蔽/可达性变化；继续运行，观察水分和鼠妇活动响应；保存退出；重开恢复同一批生物和资源，昼夜渐变对齐。

验收须记录实际观察与模型输入输出，不能仅凭一段会动的画面判定生态反馈成立。

## 8. 变更记录格式

每个重要改变记录：日期、原决定 ID、原行为、新行为、原因、影响模块、旧存档影响、验证办法、用户确认依据（若涉及重大体验变更）。用户后续明确指令优先于旧文档。文档间出现矛盾时应定位并解决，不能根据自己喜欢的版本任意选择。
