# 产品需求与首版范围

版本：审查资料 v0.1  
日期：2026-11-24  
项目工作名：微缩生态系统；正式名称待定。

## 1. 当前任务与状态说明

本资料供 Codex 首轮审查及之后的开发使用。当前阶段只允许读取资料、核查依据、检查已有工程、整理审查报告与提出修改建议。首轮不得直接创建产品工程、安装依赖、实现功能或生成大量正式素材。审查发现影响产品方向的缺口时，应集中向用户提问；得到用户明确开工授权后才进入开发。

授权的范围以用户后续原话为准。若用户授权按完整计划开发，可在该范围内持续推进各里程碑并报告结果，不必每阶段重新进行形式性确认；若只授权 M0，则完成 M0 后停止，等待扩大授权。出现新的重大产品取舍或超出授权范围时再集中说明。

全文使用三种状态：

| 标记 | 含义 | Codex 应怎样处理 |
| --- | --- | --- |
| D | 用户明确表达的目标或选择 | 保留；发现冲突时说明证据与影响，不能自行替换 |
| B | 已讨论并获得总体认可的工作基线或默认建议 | 可据此评估方案；提出调整时记录理由与影响 |
| O | 尚待审查、验证、校准或选择的细节 | 区分工程选择与用户决策，避免所有细节都变成问卷 |

这里的“完整首版”包括两个主题、编辑器和桌面组件体验；“首个闭环”是开发顺序中的较小里程碑，不代表删掉完整首版目标。

## 2. 产品定位

用户在 Windows 电脑上搭建一个独立的小型生态世界，放入生物，观察生命活动和环境变化。软件既提供可以认真布置与观察的窗口，也可以作为日常桌面组件存在。

“真实”主要指生物之间、生物与环境之间存在连续且可解释的相互影响。画面采用精细、具有空间层次和光照氛围的像素插画风格。生态过程、画面表现和实用组件共同构成产品体验。

用户在当前阶段是个人创作者与观察者。首版围绕单机本地使用组织，无账户、社交、排行榜、付费系统和多人协作的既定需求。此范围安排属于 B；未来若要加入，需要单独讨论。

## 3. 关键用户体验

### 3.1 从主题开始创作

用户先选择“林下环境”或“浅水池塘”，查看典型预设，再选择使用预设、修改预设或从空白开始。预设应提供一个可理解、可编辑的起点，并能复用于模型回归测试。

### 3.2 布置会影响世界

移动石块、增加植被、放入生物等操作应通过定义好的空间、资源和生物规则产生后续影响。仅装饰的元素应有明确标记，避免让用户误以为它们参与了模拟。

### 3.3 再打开时接着生活

关闭程序、电脑睡眠或关机期间不补算生态变化。重开后恢复原有个体与环境，再逐步对齐当前的现实昼夜目标。桌面时钟显示实际时间。

### 3.4 日常陪伴与深入观察

小组件适合长期观看和时间等信息展示；大窗口适合欣赏细节、检查状态和编辑。窗口大小和显示方式改变，不改变世界的实际尺度、资源量或个体身份。

## 5. 分期范围

| 方面 | 首个林下闭环 | 完整首版 | 后续方向 |
| --- | --- | --- | --- |
| 生态主题 | 一个林下预设 | 林下与浅水池塘 | 更多主题与容器模式 |
| 生态过程 | 水分、遮阴、基本摄食与分解反馈 | 两主题对应的生长、生命阶段、资源与环境循环 | 更完整化学、疾病、遗传、更多营养级 |
| 创作 | 选择与移动物件、必要参数；调试级试运行复制、整体加速和丢弃 | 主题素材、区域笔刷、放置生物、撤销、试运行采用和另存 | 更复杂地形、内容制作工具 |
| 世界 | 一份世界与可靠存档 | 多世界、复制、预设另存与独立运行 | 世界导入导出、版本迁移增强 |
| 展示 | 大窗口与基础小组件 | 可组合面板、独立时钟、状态组件、布局保存 | 更多实用组件 |
| 画面 | 一张风格达标的林下样板及真实状态映射 | 两主题必要素材、昼夜、生命周期和明确覆盖范围的季节表现 | 更丰富季节变体与特效 |
| 诊断 | 核心状态与资源检查 | 可收起的观察记录与趋势 | 更深入生态分析工具 |

完整首版的季节控制需要有世界日历和主题驱动入口；视觉素材可以分批补齐。必须在版本说明中区分“季节逻辑已实现”“当前主题视觉变化已实现”和“尚未提供的季节内容”。

分期按开发计划落实：M0 进行画面、双视图、Windows 生命周期和基础毛玻璃能力实验；M1 完成林下闭环及最小试运行；M2 完成浅塘与相应生态补全；M3 集成完整试运行、组件布局、离开计时覆盖和两主题季节视觉。M0 的覆盖示意不能替代 M3 的完整交互验收。

候选物种和具体参数并非所有内容都已冻结。它们应按生态文档确认作用、资料依据和校准方式。

## 6. 信息结构

建议的顶层入口：

1. 我的世界：新建、打开、暂停、复制、查看状态。
2. 主题与预设：主题说明、典型环境、从预设创建。
3. 生态编辑：场景画布、素材、工具、对象与属性。
4. 观赏：大画面、局部观察、按需展开的状态信息。
5. 工作区：组件创建、位置尺寸、层次与世界绑定。
6. 设置：运行策略、时间同步、显示、存储位置及相关平台设置。

这些入口可以合并为侧栏或面板，不强制六个独立窗口。首轮审查应检查信息结构能否用清晰、少层级的界面完成。

## 7. 对象身份与用户语义

### 7.1 主题

主题定义一类生态环境的规则、素材与候选生物；不保存某个个体当前的年龄。

### 7.2 预设

预设是一套可实例化的初始方案。内置预设有独立版本，个人修改默认另存，不回写内置内容。

### 7.3 世界

世界是实际运行中的独立实例，包含生物身份、环境资源、时间和历史。复制当前世界创建新的世界身份，同时明确复制的是当前状态。

### 7.4 视图与组件

一个生态视图绑定一个世界；多个视图可以绑定同一世界。关闭视图不等于删除世界。独立时钟无需拥有生态世界；环境信息组件必须显示其绑定的世界名称。

### 7.5 工作区

工作区保存面板与组件布局。改变工作区不会改动生态地形，恢复布局也不应回退世界进程。

## 8. 时间与现实同步的产品规则

- 桌面时钟始终显示现实时间，暂停世界和试运行加速都不改变时钟。
- 世界累计运行时间只统计被推进的生态时长，退出和电脑睡眠不补算。
- 当前光照和昼夜过渡状态属于世界状态，需要保存。
- 实际日期、时区与太阳升落时间并非同一个输入。若提供真实日出日落同步，需要地点或明确的日照时间表；首版可以先采用用户配置或主题默认时间表。
- 世界季节随世界日历推进是 B；是否额外同步现实日期属于 O，默认不暗中加入。
- 温湿度、水量、氧气和生物状态通过过程响应外部条件，不能因切换世界而套用另一个世界的数据。
- 加速试运行应显示倍率和“试运行”身份，退出后恢复日常运行策略。

## 9. 生态结果与用户干预

允许用户观察衰退、资源不足和死亡；默认使用温和、可解释的呈现方式。具体尸体图像的持续时间和表现程度属于视觉细节，由素材方案评估，不应擅自引入惊吓或强提醒。

用户干预要有明确语义：

| 干预 | 世界层含义 |
| --- | --- |
| 添加植物或动物 | 输入生物量和新身份，记录用户操作 |
| 移走生物或有机物 | 明确的输出，不当作自然死亡 |
| 移动物件 | 改变位置与相关空间属性，保留对象身份 |
| 补水或移除水 | 明确的水与溶质收支 |
| 恢复检查点 | 回到一份完整过去状态，并显示恢复结果 |
| 修改显示布局 | 仅影响观看方式 |

“健康”“肥沃”等综合描述需能展开已计算的依据。文字解释仅使用真实记录的过程，不把相关性描述为已经证明的唯一原因。

附着关系采用 B 工作默认：真正附着在基底上的苔藓或生物膜随基底移动，资源量和身份保持；移除基底时将相关附着物一并作为外部输出，原子记账。仅站在表面的动物不等同于附着物；移动或移除导致其无合法位置时，需要先明确安置，或拒绝本次操作，不能暗中删除动物。撤销恢复完整批次，细节见交互文档。

水域编辑采用 B 工作默认：新建预设时可构造多个独立水域；已有世界暂只允许不改变水域连通拓扑的形状编辑，并根据既有水量重求水位。动态分池、合池属于 O，由 Codex 审查其物质、实体和身份迁移方案后决定范围，当前不承诺完整支持。

## 10. 本地数据与非功能要求

- 数据可靠性优先于短暂视觉变化；命令结果与保存失败必须给出明确反馈。
- 世界状态、内容定义、布局和缓存分开管理。
- 用户可识别保存进度、保存失败和恢复来源；未成功保存时不能显示成功。
- 内容缺失或版本不兼容时，保留原文件并解释受影响部分。
- 性能指标在实机原型后建立，不预先承诺未经测量的 CPU、GPU、内存、帧率或世界数量。
- 状态诊断、日志和导出应避免自动包含不必要的个人路径与系统信息。
- 首版不预设自动联网上传世界、遥测或云同步。
- 安装包、升级方式、最低 Windows 版本与测试机配置属于技术审查事项；最终写入兼容性说明。

## 11. 首轮审查需要集中核实的关键问题

以下为 O。Codex 应先给出建议及影响，只有改变用户体验或成本的选择才要求用户决定。

| 问题 | 当前建议 | 为什么值得审查 |
| --- | --- | --- |
| 关闭最后一个窗口后怎样处理 | 提供清晰的“退出程序”；最后视图关闭是否退出或留托盘需明确 | 会决定世界是否仍在运行，直接影响用户对“关闭”的理解 |
| 桌面组件的窗口层级 | 首版先实现普通可定位的组件面板；是否必须嵌在桌面层、置顶或鼠标穿透需核实 | 影响 Windows 集成范围与交互，用户尚未逐项要求 |
| 视觉生产路线和质量基准 | 用原参考图制作一个原创林下样板，再确定素材规模与制作方式 | 直接影响最受重视的画面效果与开发工作量 |
| 首版季节内容的深度 | 保留季节驱动，并明确两主题实际提供的视觉阶段 | 避免只做时间参数却把完整四季表现算作已交付 |

常规问题如代码命名、包管理器、文件编码、内部数据容器和调试界面位置，Codex 应给出合理工程方案，不必逐项询问用户。

## 12. 审查输出与开发入口

首轮输出统一放到：

- review/01-audit.md：覆盖范围、冲突、缺口、风险及来源位置。
- review/02-questions-and-decisions.md：少量高影响问题、建议、用户答复及决定。
- review/03-implementation-plan.md：按依赖排列的开发计划、任务和验收。
- review/04-readiness.md：是否具备开工条件、剩余阻塞项和明确授权状态。

“通过审查”意味着资料足以启动指定里程碑，不意味着生态参数已获科学验证、视觉已达标或 Windows 性能已测量。首轮完成后停止在审查结果，等待用户明确授权开始开发。

进入开发后的阶段报告用于展示结果与问题，不自动形成逐阶段审批门槛；后续行动遵循实际获得的授权范围。

## 13. 需求依据

需求来源为本次项目讨论中用户的原始描述与后续确认，以及已获得总体认可的《首版生态模型与系统架构 v0.1》。D、B、O 的区分用于保留这些来源的强弱；参考图提供视觉目标，不自动增加其中出现的所有生物、人物或建筑功能。
