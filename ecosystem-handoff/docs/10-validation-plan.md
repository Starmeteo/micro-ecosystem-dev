# 验证计划与验收证据

版本：0.1 审查草案。日期：2026-11-24。本文定义未来的验证要求；资料整理阶段没有执行产品测试，也没有 Windows 性能实测结果。

## 1. 验证目标与证据等级

验证围绕生态结果、连续生活、可编辑性、像素画面与 Windows 日常使用展开。选择能发现具体错误的测试，避免仅照抄实现或对每次低风险文字调整增加测试负担。

| 证据等级 | 可以说明什么 | 不能替代什么 |
| --- | --- | --- |
| 资料审查 | 需求一致性、模型范围、技术依据与已知缺口 | 已实现功能、实际性能 |
| 静态检查与构建 | 类型、语法、基本依赖和构建可行 | 用户流程、生态正确性、系统睡眠行为 |
| 无界面核心验证 | 固定输入下的状态、资源、时间与可重复性 | 视觉品质、Windows 图形兼容 |
| 集成与界面验证 | 命令、快照、编辑流程、组件状态 | 未实际测试的系统/硬件环境 |
| Windows 实机验证 | 记录环境中的窗口、DPI、睡眠、安装和负载表现 | 所有设备和驱动上的普遍保证 |
| 模型校准 | 在明确物种与条件范围中的数值适用性 | 对未建模生态过程的科学预测保证 |

没有对应证据的项目写“未验证”，不能写“通过”。

## 2. 固定验证输入

每个可重复场景记录：模型版本、内容定义版本/摘要、初始世界状态、随机算法与完整状态、步长方案、输入序列、命令序列、预期性质、误差容限及其依据。

开发回归使用固定气候、日夜与干预输入。实时现实时间和天气用于体验验证，不能作为要求严格复现的唯一输入。

### 2.1 场景集合

| 场景 ID | 内容 | 主要目的 |
| --- | --- | --- |
| FIX-FOREST-BASE | 林下基础布局、少量动物、有限枯落物与已声明边界输入 | 验证完整循环和保存恢复 |
| FIX-FOREST-SHELTER | 基础场景加一组记录的石头移动操作 | 检查旧、新位置的遮蔽/水分/行为变化 |

## 3. 生态与资源不变量

### VAL-ECO-001 物质收支

对每个追踪的物质分别计算：初始存量 + 边界输入 − 边界输出 − 当前存量。内部转移应相互抵消，残差不得超过事先定义的数值误差预算。

核对位置包括环境库、生物体、储备、排出物、死亡物和微生物生物量。浓度不能与总质量直接相加；能量与物质使用不同账本。没有完整元素追踪时，只对实际实现的账本作守恒声明。

### VAL-ECO-002 有限资源竞争

多个消费者同时摄食相同资源，总消耗不超过供给；更换容器遍历顺序不应产生未声明的系统优势。输入不足时按明确规则分配，而不是独立给每个消费者完整需求。

### VAL-ECO-003 生命周期转移

死亡、繁殖、生长和排出物的产生具有对应来源/去向。复制世界不向原世界额外增加物质；新增生物或投放食物被记为外部输入。

### VAL-ECO-004 非负与有限值

资源、体积和需要非负的状态保持合法范围。负质量、NaN、无穷值等错误应被发现并定位；任意钳到零后继续运行，不能作为守恒已经通过的证据。

### VAL-ECO-005 水量与浓度

对模型中不会随蒸发离开的溶质，蒸发减少水量并改变浓度，但不按同一比例减少该溶质质量。排水带走多少溶质由实际排出水体和其浓度决定。补水使用输入水自身的物质组成。水域不连通时不能自动共享资源。

### VAL-ECO-006 氧过程不重复

把所有氧输入与输出列成过程清单。已通过某反应计入的微生物耗氧不能再额外算一次；夜间变化来自光合和呼吸等过程，不追加一个无法对应过程的夜间扣氧量。没有局部溶氧分区时，行为模型不能声称感知到同一水体中不同位置的氧差。

### VAL-ECO-007 条件明确的生态方向

在其他条件固定、过程适用的范围内，验证遮阴、水分、食物限制、光照和有机物负荷的响应。报告完整条件，不把单一条件下的方向推广到所有生态状态。种群长期恒定、永不崩溃或每次都出现漂亮周期不作为验收要求。

### VAL-ECO-008 食物与生物膜分类

米虾、水蚤等只消耗其配置允许的资源。生物膜中的组成已经归属于某状态库时，不再作为另一份独立质量加入总量。分解、悬浮食物与附着食物之间的转换明确记录。

## 4. 时间 连续性与可重复性

| 验证 ID | 操作 | 通过条件 |
| --- | --- | --- |
| VAL-TIME-001 | 相同状态/输入/RNG，以不同绘制频率运行到相同步数 | 同平台同版本核心结果一致；渲染不参与生态状态更新 |
| VAL-TIME-002 | 无视图、一个视图、两个视图分别观察同一世界 | 运行时间与资源结果一致，不重复推进 |
| VAL-TIME-003 | 暂停后经过现实时间再恢复 | 暂停段不增加生态进度，恢复无巨大首步 |
| VAL-TIME-004 | 退出后隔很久加载 | 读取已保存状态，不计算离线代谢或衰老 |
| VAL-TIME-005 | 真实 Windows 睡眠/休眠后恢复 | 睡眠时长不进入生态；原暂停状态保留 |
| VAL-TIME-006 | 普通 CPU 忙碌造成调度积压 | 不误标离线；按既定过载策略处理并有真实状态反馈 |
| VAL-TIME-007 | 在昼夜过渡中保存并改变现实目标后加载 | 当前环境连续，目标更新可追溯，资源不在加载瞬间突变 |
| VAL-TIME-008 | 跨午夜、时区改变、系统时间前后调整 | 生态累计时间不倒退；时钟显示与相位规则符合配置 |
| VAL-TIME-009 | 试运行加速与受控正常速度比较 | 在相同模拟时间和步长方案下结果一致或符合事先定义的容差 |
| VAL-TIME-010 | 保存完整状态后分别继续原实例与恢复实例 | 对同一后续输入，随机行为和资源变化可复现 |
| VAL-TIME-011 | 编辑未结束时退出，再打开应用 | 恢复为暂停，保留运行意图及编辑恢复入口；不自动推进 |
| VAL-TIME-012 | 运行态、手动暂停态、编辑暂停态分别经历系统挂起 | 恢复到挂起前有效意图；移除系统挂起原因，不移除用户/编辑暂停 |
| VAL-TIME-013 | 采用加速试运行结果 | 采用世界时间/RNG/当前节律，保持正式运行意图，使用日常倍率与驱动连续对齐 |

改变模型步长后的结果通过收敛/误差实验比较，不要求所有浮点结果逐位相同。改变内容定义或算法版本时也不能直接拿旧快照的逐位比较作为唯一正确性标准。

### 4.1 世界季节验证

| 验证 ID | 操作 | 通过条件 |
| --- | --- | --- |
| VAL-SEASON-001 | 暂停世界并经过现实日期变化 | 世界日历与季节保持暂停；现实钟可变化 |
| VAL-SEASON-002 | 退出后跨现实季节重新打开 | 世界季节从保存状态继续，不按离线现实日期跳季 |
| VAL-SEASON-003 | 受控输入下整体加速与日常倍率推进相同模拟时长 | 日历、季节驱动与对应生态过程一致或处于已声明容差 |
| VAL-SEASON-004 | 推进至世界跨年、季节边界并保存恢复 | 周期、跨年和过渡连续，阶段事件不重复执行或遗漏 |
| VAL-SEASON-005 | 两世界不同日历/气候/暂停状态，反复切换视图 | 季节分别推进，切换不复制另一世界的季节或参数 |
| VAL-SEASON-006 | 改变现实日夜目标并保持世界季节来源 | 两驱动按配置组合，光照相位对齐不重置世界日历 |
| VAL-SEASON-007 | M3 季节素材和颜色呈现 | 读取同一模型季节状态，不以渲染帧或现实日期另算季节 |

## 5. 命令 视图与编辑流程

| 验证 ID | 操作 | 通过条件 |
| --- | --- | --- |
| VAL-IPC-001 | 重发同一添加生物命令 | 有效代次内只执行一次，返回一致回执 |
| VAL-IPC-002 | 相同命令 ID 携带不同内容 | 明确拒绝而非随机采用某一份 |
| VAL-IPC-003 | 从 A 切到 B 后迟到 A 的快照 | B 画面与数据不受污染 |
| VAL-IPC-004 | 恢复检查点后迟到旧运行代次数据 | 拒绝旧数据并保持新基线 |
| VAL-IPC-005 | 让视图接收变慢 | 可合并视觉快照；可靠回执和重要事件仍可获取 |
| VAL-IPC-006 | 两个界面同时提交相同编辑修订 | 明确串行结果或冲突，不出现半次编辑 |
| VAL-IPC-007 | 模拟继续运行期间提交合法编辑 | 不能仅因 tick 增长而总是发生 editRevision 冲突 |
| VAL-EDIT-001 | 移动一块石头 | 旧、新位置的遮蔽、通行和相关环境属性都更新 |
| VAL-EDIT-002 | 拖动中取消、提交、撤销与重做 | 预览不改正式资源；一次操作具有清楚撤销边界 |
| VAL-EDIT-003 | 改变场景显示尺寸或相机 | 生态物理面积、水量、动物尺寸与数量保持原值 |
| VAL-EDIT-004 | 深拷贝试验副本、整体加速并丢弃 | 副本新 worldId，entityId 可保留；RNG 数值可相同但不共享实例，原世界完整状态保持不变 |
| VAL-EDIT-005 | fork 基线仍有效时明确采用试运行结果 | 保留正式 worldId/运行意图，只采用生态状态、世界时间、RNG、当前节律；恢复日常倍率/驱动，全部视图切到新代次 |
| VAL-EDIT-006 | 创建预设、复制现状、从预设创建 | 初始方案与正在生活的状态复制语义明确 |
| VAL-EDIT-007 | 正式世界继续推进、编辑、重新加载或恢复后采用旧副本 | 任一 fork 基线 world/run/edit/tick 不匹配时明确冲突，保留原世界和副本，不静默覆盖 |
| VAL-EDIT-008 | 两个世界内存在相同 entityId，跨视图交错消息 | 以 worldId + entityId 定位并检查 runGeneration，不串实体状态 |

## 6. 存档与故障恢复

至少覆盖正常保存、自动检查点、内容版本缺失、不支持格式、损坏文件、磁盘写入失败、文件被占用、临时文件写到一半终止、替换提交中终止、索引未更新等情况。

| 验证 ID | 场景 | 通过条件 |
| --- | --- | --- |
| VAL-SAVE-001 | 在合法步骤边界保存 | 文件内部的时间、实体、资源和待处理过程一致 |
| VAL-SAVE-002 | 候选文件写入失败 | 上一有效检查点保持可读，错误可见 |
| VAL-SAVE-003 | 保存不同阶段模拟终止 | 能恢复明确的已提交检查点；不读半文件 |
| VAL-SAVE-004 | 最新检查点损坏 | 不覆盖原件，可明确回退到上一有效版本 |
| VAL-SAVE-005 | 旧内容定义版本不存在 | 清楚拒绝或走经验证迁移，不静默使用最新参数 |
| VAL-SAVE-006 | 执行结构/模型迁移 | 保留源数据，迁移结果通过对应不变量和预期变化检查 |
| VAL-SAVE-007 | 未支持的新格式被旧应用打开 | 清楚提示，原文件不被重写破坏 |
| VAL-SAVE-008 | 恢复布局时显示器已断开 | 窗口和关键控件可找回，世界数据不变 |

开发时可以先通过存储接口故障注入验证流程，再对真实 Windows 文件行为作集成验证。自动保存频率不能替代文件一致性与失败恢复测试。

## 7. 视觉与交互验收

视觉依据为用户提供的 REF-01 至 REF-09 和 [视觉与素材规范](08-visual-and-asset-guide.md)。参考图中的人物、海洋大型动物或建筑不自动进入首版功能范围。

对林下、浅塘分别保留大窗口和小组件的实际截图；使用固定的场景、相机与昼夜条件进行版本比较。截图应反映真实产品状态，不能用离线绘制的一张高质量图代替实际场景表现。

| 维度 | 检查内容 |
| --- | --- |
| 像素语言 | 像素密度一致、轮廓有意组织、细节具有层次，避免无意义噪点 |
| 色彩与光照 | 色调统一、明暗关系清晰，夜间仍保留合理可读性 |
| 空间 | 前中后景、遮挡、接触关系和水下深度明确 |
| 小尺寸可读性 | 主要生物、环境变化与时钟可以辨认，细节不挤成一片 |
| 动作 | 个体移动与当前行为相符；动画不改变权威状态 |
| 编辑反馈 | 选中、预览、非法位置、提交与撤销状态可理解 |
| 布局模式 | 调整组件不会误操作生态；叠放与边界可发现 |
| 毛玻璃覆盖 | 延迟与恢复自然，编辑/输入期间不会遮挡必要操作 |
| 观察说明 | 数值单位、模型简化与事件依据明确，未实现指标不伪装精确读数 |

评价采用“通过 / 需要修正 / 严重偏离”，并写具体位置和改法。视觉样板的第一次评审重点确认方向，后续不要求用户逐个精灵批准。

## 8. Windows 与性能矩阵

M0 先确定实际测试设备与支持范围。记录：Windows 版本/构建、CPU、内存、GPU/驱动、WebView2、渲染后端、依赖版本、显示器分辨率/DPI、窗口尺寸、场景实体规模、世界数和视图数。

| 测试组合 | 观察指标 |
| --- | --- |
| 单世界大窗口 | 帧耗时分布、输入延迟、核心步进耗时、CPU/GPU 与内存 |
| 单世界常态小组件 | 持续资源消耗、视觉可读性和时钟覆盖切换 |
| 同世界双视图 | IPC 数据量、渲染开销，确认核心仅一次推进 |
| 双主题多世界 | 总步进成本、后台世界的时间正确性 |
| 模糊覆盖与最小化 | 绘制优化收益，生态运行策略仍正确 |
| 改变 DPI 与跨显示器 | 像素采样、坐标映射、拖动与布局恢复 |
| 长时间运行与反复开关视图 | 内存/资源趋势、订阅泄漏、数值残差 |
| 目标范围内较弱设备 | 可用模式、降画面负载策略和明确的过载反馈 |

记录中位数、较慢尾部表现或其他说明清楚的统计，而不只写瞬时峰值。CPU、GPU、内存、功耗、帧率和最大世界数量的合格线由 M0 实测与产品目标共同确定。当前没有足够证据填入承诺值。

若没有对应设备、权限或测试能力，报告缺口与具体复测步骤。不能把浏览器测试标记为 Windows 原生生命周期测试。

## 9. 阶段验收映射

| 阶段 | 最低相关验证 |
| --- | --- |
| R 审查 | 文件完整、9 图阅读、D/B/O 一致、重大歧义与开工条件 |
| M0 | VAL-TIME-001/002、VAL-IPC-003/004、最小保存、Windows 生命周期实验、视觉样板 |
| M1 | 林下相关 ECO、TIME、EDIT、SAVE 组；石头编辑到保存恢复完整流程；最小试运行深拷贝/整体加速/丢弃 |
| M2 | 水量/浓度/氧/食物分类、两主题生命周期补全、日夜与压力场景、季节模型 VAL-SEASON-001 至 006、参数校准 |
| M3 | 世界隔离、可靠回执、试运行采用/另存及 fork 冲突、完整 idle 覆盖、组件与布局、多屏恢复、季节视觉 VAL-SEASON-007 |
| M4 | 未关闭的重大缺陷复测、历史存档、长期运行、安装及实际性能范围 |

严重破坏资源、保存、时间和世界隔离的问题阻止受影响阶段交付。低影响问题可以列入已知限制，但需要明确影响和后续任务。

## 10. 验证记录模板

每项记录包含：验证 ID、关联需求/任务、软件提交与内容版本、环境、输入、操作、预期性质、实际观察、数值/截图/日志证据、结果、限制和缺陷链接。自动检查只覆盖可客观比较的部分；审美与交互判断写清观察依据。

首轮审查的 `review/04-readiness.md` 应把“文档可进入开发”和“产品已经验证”分开，统一采用 `BLOCKED`（资料/技术阻塞）、`NEEDS_DECISION`（产品取舍）、`READY_WITH_TRACKED_WORK`、`READY` 四态。当前资料达到前者的条件需要 Codex 审查；后者只能由后续实现与真实测试产生。

首轮审查结束必须等待真实开工授权。后续验收是判断已实现结果和阶段风险，不自动增加逐阶段审批：用户授权完整计划时可在范围内连续推进，授权仅覆盖 M0 时在 M0 后停止。
