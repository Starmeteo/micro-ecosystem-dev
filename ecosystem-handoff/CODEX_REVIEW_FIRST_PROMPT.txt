三、先确认你理解的项目

请基于资料概括项目，而不是用泛化的“生态游戏”“动态壁纸”概念代替具体目标。应包括：

1. 用户在编辑器里布置环境、放入生物，观察生物之间以及生物与环境之间的持续反馈。
2. “真实”重点在生态因果关系；视觉采用精细、有空间层次和自然氛围的像素插画表达。
3. 主要保持一个精心布置的主视角，通过遮挡、比例、色彩和光照表现空间，允许局部观察。
4. 首版目标包含林下和浅水池塘。主题下提供典型预设，支持修改另存和自由搭建。
5. 多个世界独立，同一世界可被多个窗口或组件查看，但只推进一次模拟。
6. 软件停止、电脑睡眠或关机期间不做生态补算；重新打开恢复原有世界，昼夜再逐步对齐现实。桌面时钟显示真实时间，各世界保留自己的气候。
7. 既有大窗口观赏，也有常态小组件；鼠标离开一段时间后可出现模糊覆盖和时钟。时钟与其他组件可以独立创建、叠放或在面板中自由摆放。
8. 暂定技术栈是 Tauri 2 + React 19 + TypeScript + PixiJS 8 + Rust。具体版本需核查，技术栈的大方向不应随意推翻。

资料中的 D 是明确用户决定，B 是当前工作基线，O 是待审查/研究/校准。请保留这一差别。要变更已确认方向时，先说明证据、问题和影响。

四、进行真正的审查

至少从以下十个方面检查，并引用具体文件、章节、需求或决定编号。

1. 产品完整性与范围
目标是否清晰？完整首版与第一个里程碑是否区分？有没有把示例当成硬性需求？核心生态、编辑器、组件和多世界之间有没有缺少的流程？用户上传的参考图是否被误读为必须加入图中所有生物、人物或场景？

2. 用户操作与生命周期
创建、编辑、撤销、试运行、采用结果、存为预设、复制当前世界、删除、切换世界和退出是否语义一致？关闭主窗口、关闭一个组件、隐藏托盘、最小化和真正退出是否有歧义？组件布局编辑会不会误改生态世界？

3. 时间规则
真实时钟、累计模拟时间和当前环境节律是否分开？离线、睡眠、普通计算积压、手动暂停和试运行加速是否得到不同处理？跨午夜、时区或系统时间变化会怎样？季节跟随世界时间与现实昼夜目标是否冲突？1:1 日常速度是否能给用户足够可感知的变化？

4. 生态模型与科学假设
个体、斑块、种群和环境单元的计算精度是否一致？状态和参数单位是否完整？食物、生物量、排出物、死亡、分解和养分有没有重复或丢失？外部输入是否显式记账？有限资源竞争是否合理？微生物和生物膜是否重复计算，氧气消耗是否重复扣除？
特别检查：充分混合水体不能伪造局部氧梯度；省略硝化等化学过程就不能冒充完整水质预测；候选物种不等于已经验证的稳定混养组合；来源论文支持机制不等于本模型已校准。

5. 架构与通信
Rust 权威状态、纯生态内核、运行层、Tauri 适配、React 交互和 PixiJS 绘制的职责是否明确？是否能无画面运行和验证？多视图会不会重复模拟？不同世界会不会串状态？worldId、runGeneration、commandId、editRevision 和 tick 是否有独立语义？过期快照、命令重试、背压和错误结果怎样处理？

6. 数据与存档
预设、物种/材料定义、世界实例、视图和工作区布局是否分离？存档是否保存完整随机状态、环境过渡、资源、生命阶段和定义版本？崩溃、损坏、版本迁移、试运行副本和检查点恢复是否有清晰规则？是否避免加载时偷偷替换旧物种参数？

7. 视觉与素材生产
请根据实际看到的参考图评价文档是否抓住像素形状、色彩层次、前后遮挡、水下氛围、局部对比与构图。提出可拆分、可编辑、可动画的素材生产方案和首张样板的验收方式。
缩小成组件后是否仍然清楚？DPI 和非整数缩放怎样验证？生长阶段和行为如何映射到画面？不能用粗矩形、随机噪点或单纯降低分辨率就宣称达到参考质量，也不能仅凭静态图编造原作品的帧率、动态效果或精确原始像素尺寸。

8. 技术栈与 Windows 可行性
按当前官方资料核查依赖兼容性和关键能力。关注窗口、输入、DPI、多屏、系统睡眠、WebView、绘制与后台运行。区分“文档宣称支持”“需要试验验证”“当前已经实测”；不要预先承诺未经测试的 CPU、GPU、内存或帧率。
无需为了追求更新而重选整个技术栈。如发现实质障碍，给证据、最小调整方案和取舍。

9. 开发计划与验证
M0 和林下最小闭环是否能交付？任务有没有缺少前置依赖？生态与视觉验证是否并行？有无资源守恒、同输入复现、渲染解耦、世界隔离、睡眠恢复和存档损坏等真正有价值的检查？阶段完成是否能通过可运行演示与实测证据判断？

10. 资料自身质量
检查文档互相矛盾、失效链接、缺图、占位内容、没有单位的数值、无法追溯的参数、遗漏的失败流程和未经解释的术语。清楚区分产品文档、研究任务、旧交互草图与实际实现。
