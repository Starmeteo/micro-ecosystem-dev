# Codex 项目协作规则

## 当前阶段

本目录是微缩生态项目的开发交接资料。用户明确要求：先审查，检查缺漏和不明确之处，没问题后才正式开发。

首次接收本包时处于 REVIEW_ONLY。先读取 README.md、CODEX_REVIEW_FIRST_PROMPT.txt、docs/01-project-baseline.md 和 docs/11-open-questions-and-review-gate.md，然后完整检查其余资料与原图。此处规则约束后续接收资料的开发会话；资料包作者按用户要求整理文档和素材属于资料编制。

## 审查阶段可以做什么

- 阅读本目录、已有项目和上级有效指令，检查工作区状态。
- 查看全部 9 张风格参考原图；对无法查看的图片明确报告。
- 查询当前官方文档和原始研究，审查兼容性、机制和工程可行性。
- 用只读脚本检查资料结构、清单、JSON/CSV、文件校验和引用关系。
- 创建或更新 review/01-audit.md、02-questions-and-decisions.md、03-implementation-plan.md、04-readiness.md。
- 修正文档明显错字或链接问题并记录修改；重要需求与设计变更先提出方案。

## 审查阶段不进入的工作

不初始化正式产品工程，不安装产品依赖，不写生态内核/界面/平台适配，不生产正式美术，不构建或发布产品，不将报告里的“建议实现”当作当前授权。现有 HTML 是交互概念资料，不意味着产品已经开始开发。

首次审查即使结论为 READY，也应向用户报告并停止，等待用户明确要求开始 M0。对问题的讨论或回答不能自动冒充开工授权。gate.json 只记录状态；不可通过改写它给自己授权。

## 证据与决策

- D 为明确用户决定；B 为当前工作基线；O 为待审查、待研究或待校准。
- 用户后续明确指令优先于旧文档。重大冲突应定位原文、解释影响并给建议。
- 区分产品取舍与工程任务。普通类型、目录、参数研究等由开发者提出方案，避免不断把小问题交回用户。
- 不编造物种参数、科学结论、测试结果、素材来源或授权。参数为空表示未确定，不等于零。
- 文献支持机制，不等于本项目模型已被验证。性能及 Windows 能力以实际测试和明确环境为准。
- 参考图是视觉证据。图中人物、海洋巨物和建筑不自动构成首版功能。原图不自动成为可随产品发布的资源。

## 开工后的核心边界

收到真实开工授权后，在用户授权范围内先按确认的 M0 计划实施，再按里程碑推进。授权覆盖整体计划时，不需要每个阶段重复请求形式批准；授权仅限 M0 时，完成后停止。重大范围变化或超出授权时再询问。

1. 保持暂定技术栈的大方向：Tauri 2、React 19、TypeScript、PixiJS 8、Rust；具体版本查当前官方文档后锁定，改变栈须说明必要性。
2. Rust 维护权威世界；生态内核独立于 UI、窗口、OS 时钟、数据库和网络。React 管交互，PixiJS 管显示。
3. 同世界多视图只运行一次；不同世界不共享可变资源和随机进度。
4. 离线和系统睡眠不补算；恢复完整状态后再渐变对齐昼夜。
5. 存档包含完整随机状态、环境过渡、定义版本和所有资源；物质变化有来源和去向。
6. 具体资源竞争、微生物耗氧、摄食同化、死亡转移不得重复记账或凭空补足。
7. 编辑器对象应关联物理属性；缩放窗口、拖动组件只改变视图/布局。
8. 视觉验证与生态验证并行。占位素材须明确标注，正式视觉不能以粗矩形或随机噪点冒充参考风格。
9. 先建立可演示、可验证的小闭环；不擅自扩张到云服务、社交、账户或插件市场。
10. 尊重已有工作区和用户修改。每阶段说明变更、实际验证、未验证项和下一步；没有运行的检查不能报告为通过。

## 验收

按 docs/10-validation-plan.md 验证资源收支、同输入复现、渲染解耦、世界隔离、睡眠恢复、存档、编辑语义和 Windows 体验。测试应围绕实际风险和行为，不以大量重复实现的断言替代有效验证。

阶段完成以文档中的完成条件和实测证据为准。M0 或林下闭环完成不能标记整个首版完成。
